# LeanLife 多用户轻商用 MVP 架构方案

这份方案的目标不是把当前原型一次性重写成大系统，而是把它稳定过渡到可承载轻商用、多用户、基础运营与数据合规的版本。

## 1. 本阶段最适合的落地目标

当前原型已经验证了 5 条核心链路：

1. 用户身体数据评估
2. 饮食方案选择与执行
3. 日历化身体反馈记录
4. 食物记录与营养计算
5. 方案关联的营养分析与缺口推荐

从原型过渡到轻商用 MVP，最有建设性价值的不是继续堆前端页面，而是先固定这 5 条链路背后的：

1. 数据模型
2. API 契约
3. 用户与数据隔离方式
4. 计算服务边界
5. 运营与审计基础

## 2. 推荐技术拆分

### 前端

- `Next.js`
- `TypeScript`
- 当前静态原型的视觉与交互可以迁移成：
  - `app/(marketing)`：官网与产品展示
  - `app/(app)`：登录后的工作台
- 前端只负责：
  - 采集输入
  - 展示分析结果
  - 做轻量交互状态

### 后端

- `NestJS` 或 `FastAPI`
- 统一负责：
  - 账号系统
  - 数据读写
  - 身体评估算法
  - 营养汇总计算
  - 方案联动分析
  - 缺口推荐

### 数据库

- `PostgreSQL`
- 适合原因：
  - 多用户隔离稳定
  - 事务能力强
  - JSON 字段适合保存分析快照
  - 后续做统计、后台、报表更方便

### 缓存与异步

- MVP 阶段可选：
  - `Redis`
  - 用于登录会话、热门食物缓存、计算结果短时缓存

## 3. 业务分层建议

### A. Identity 身份层

负责：

- 注册 / 登录
- 密码哈希
- 会话与 token
- 用户角色

建议角色：

1. `user`
2. `coach`
3. `admin`

### B. Profile 用户档案层

负责：

- 基础资料
- 身体静态参数
- 生活习惯参数
- 当前目标

这层数据更新频率不高，但会影响所有后续计算，所以要单独管理版本。

### C. Assessment 评估层

负责：

- BMR / TDEE
- 体脂估算
- 腰高比
- 恢复分与依从性基础分
- 推荐饮食方案
- 日目标热量与宏量营养

建议：

- 每次重新评估都保存快照
- 不覆盖历史结果
- 日志和营养分析引用“当时生效的评估版本”

### D. Tracking 追踪层

负责：

- 每日体重、腰围、主观感受
- 日历记录
- 趋势图
- 周均值

建议：

- 身体反馈记录与饮食记录按同一天关联
- 保留原始记录，不要只存汇总值

### E. Nutrition 营养层

负责：

- 食物数据库
- 单位换算
- 食物营养计算
- 每日营养汇总
- 微量元素覆盖度

建议：

- 食物数据库使用“基础单位 + 可选单位换算”
- 所有记录最终都换算成 `g` 或 `ml`
- 微量元素统一按 `100g / 100ml` 基准值计算

### F. Recommendation 推荐层

负责：

- 当前方案关联分析
- 缺口推荐
- 超标提醒
- 后续动态建议

建议：

- 推荐结果保存快照
- 前端展示时标记“建议生成时间”和“依据的方案版本”

## 4. 多用户阶段必须拆出的核心实体

### 必要实体

1. `users`
2. `user_profiles`
3. `body_assessments`
4. `diet_plan_templates`
5. `food_catalog`
6. `food_unit_options`
7. `daily_logs`
8. `body_metric_entries`
9. `food_entries`
10. `nutrition_snapshots`
11. `recommendation_snapshots`

### 为什么需要快照

轻商用系统不能只实时重算，因为：

1. 食物库后续会更新
2. 饮食方案模板会迭代
3. 算法版本会变化

如果不保留快照，用户看到的历史分析会不断漂移，客服和运营也无法解释“为什么那天是这个结果”。

## 5. API 设计原则

### 原则 1

前端不直接实现营养学核心逻辑，所有关键计算都由服务端返回。

### 原则 2

创建型接口尽量返回：

- 原始记录
- 汇总结果
- 分析结果
- 当前适用方案

避免前端再拼一次。

### 原则 3

所有按日期相关的接口都使用：

- `user_id`
- `log_date`
- `timezone`

避免日历错位。

### 原则 4

所有分析接口返回：

- `algorithm_version`
- `assessment_id`
- `plan_id`

方便回溯。

## 6. 轻商用必须补的安全与合规

### 最低要求

1. 密码哈希存储
2. 访问令牌过期
3. 用户数据隔离
4. 基础操作日志
5. 删除账号与导出数据能力
6. 隐私政策与免责声明

### 特别注意

这个产品涉及身体数据与饮食建议，必须明确写出：

- 非医疗建议
- 不替代医生或注册营养师诊断
- 对孕期、进食障碍、重度慢病用户有限制提示

## 7. 运营侧最低能力

MVP 阶段至少要有一个轻后台，用来：

1. 管理食物库
2. 管理饮食方案模板
3. 查看用户反馈与异常日志
4. 下架不合适的推荐规则

## 8. 推荐的迭代顺序

### Phase 1

先搭后端与数据库骨架：

1. 账号系统
2. 用户档案
3. 每日记录
4. 食物库
5. 分析接口

### Phase 2

把当前前端迁到真正的应用层：

1. 登录
2. 用户工作台
3. 日历追踪
4. 饮食记录工作台

### Phase 3

补运营与商业化基础：

1. 管理后台
2. 数据导出
3. 埋点与异常告警
4. 订阅或会员权限

## 9. 当前项目最值得先做的一步

在当前原型基础上，最有价值的第一步就是：

1. 固定数据库结构
2. 固定 API 契约
3. 让营养分析与推荐逻辑有明确服务端边界

这一步完成后：

- 可以继续保留当前前端视觉原型
- 可以并行开发后端
- 可以逐步迁移成真正多用户系统

后续实现时，请优先参考：

- 数据库结构：`backend/schema.sql`
- API 契约：`backend/openapi.yaml`
